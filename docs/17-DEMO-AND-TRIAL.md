# ReviewRadar: demonstration and genuine-contributor trial

Prepared 24 October 2026. This is a script and trial invitation, **not a completed recording or participant result**. The later bounded rendered checks are recorded in `18-FINAL-BROWSER-AND-LIFECYCLE-AUDIT.md`; this script is not itself proof of a recording or participant result.

## What the demonstration must establish

A contributor can recover the context of a review request, inspect a possible later response, write the next thing they intend to check, and retain a source-linked review sheet. It must also make three distinctions clear: historical versus fresh evidence, a conversational reply versus a verified fix, and a local decision versus a GitHub action.

The public replay is usable without a model or account. Fresh GitHub intake and Gemma inference require the local application and the installed runtime/model. The pinned model artifact is 2,841,481,184 bytes, about 2.84 GB; the download and setup are part of adoption cost, not an invisible prerequisite.

## Recording preparation

- Use only public, non-confidential PRs. Hide account credentials, session headers, terminal environment values and unrelated browser tabs. Never display the model key or app session token.
- Record the actual running application, not an animation reconstructed to look like inference. No recording is claimed until a real file exists and has been reviewed.
- Begin with an empty demonstration note or clearly identify any pre-existing local note. Do not erase the user's genuine notes to prepare a recording; use a separate test workspace or a designated demo analysis.
- Verify the app and model are ready before recording. The macOS launcher is scoped to the current login session; stopping it or logging out ends availability. This is not a permanently hosted backend.
- For the live portion, use the actual read-only import of `https://github.com/fossasia/eventyay/pull/6104` with owner `YashAnand69`. Show the new capture time and coverage; do not reuse the curated replay's completeness or inference timing as if it came from that fresh import.
- Do not promise the model will emit the saved pair verbatim. If inference fails or proposes a poor interpretation, show the actual state and explain it; retry visibly or use a separately labelled recorded historical result. A baseline result is never a Gemma result.
- Only describe a rendered/mobile/keyboard check as complete after it has been performed on the actual final build. An agent-operated demonstration is not a real-user validation session.

## A 60–90-second actual-app script

Timing is a target, not permission to hide waiting. Show elapsed model time. If processing or import takes longer, keep the wait, extend the recording, or explicitly label a cut and state the measured wait from that run. Do not accelerate the recording and present it as ordinary latency.

| Target | Actual action | Suggested explanation |
| --- | --- | --- |
| 0–12 seconds | Open the public replay and select the Eventyay screenshot request. Keep the capture date and incomplete-source notice visible. | “This is a saved historical example, not my current inbox. The reviewer asked for screenshots; a later author update reports adding them.” |
| 12–25 seconds | Show both source passages and open their original/full context. | “The pair helps me find the conversation. It does not prove the screenshots meet the request. The model's rationale can overstate that, so its interpretation remains explicitly unverified.” |
| 25–45 seconds | Switch to the local app. Import the one public PR and choose **Analyse locally**. Show actual fetch date, human-review scope, model identity and elapsed time. | “This is a fresh, read-only GitHub import. Local Gemma proposes the individual asks and considers later author responses. The public page did not run this model.” |
| 45–60 seconds | Inspect the actual result, including any incomplete/uncertain state. If helpful, briefly show **Chronology baseline**, then restore the desired saved model analysis through **Saved analyses**. | “The baseline orders human-review comments. Gemma proposes the semantic pairing. Neither verifies code, and I still inspect the original source.” |
| 60–78 seconds | Write and save a demo note: “Inspect the attached screenshots against the requested behavior before following up.” Mark reviewed locally, reopen, and download the review sheet. | “This is the next check I chose. Saving and reopening change only this local review record. The export retains the evidence and its dates.” |
| 78–90 seconds | Show the replay/setup/source links and the review sheet. | “The useful output is a small source-linked reading plan. There is no GitHub write or measured human time-saving claim. The installed engine and the public saved replay have different roles.” |

If fitting both replay and live intake makes the recording rushed, prefer a clear longer take. The challenge requires a demo link or video; the existing replay is a demo link. A new video should add genuine evidence rather than become a fabricated completion checkbox.

## Evidence boundaries

| Material | What it supports | What it does not support |
| --- | --- | --- |
| Public saved replay | Interaction with three recorded model cards over six attributed selected source bodies; local browser decisions/export | Live inference, complete PR history, current outstanding obligations, general accuracy |
| Fresh local GitHub import and Gemma run | That captured input's read-only intake, actual model execution, source pairing and recorded runtime | A different snapshot's completeness/results, average performance, correctness of the code change |
| Frozen engineering pilot | The documented version-specific development/holdout/regression observations on four PRs and seven assistant-created labels | Independent human ground truth, a fresh holdout after tuning, a population accuracy or demand estimate |
| Synthetic/adversarial tests | Specific controlled failures: invalid references, malformed data, timing/order, recovery and state transitions | Real participant experience, real-world demand, a production workload or endorsement |
| Genuine contributor trial, if performed | That person's observed comprehension, actions, confusion and correction burden, with the recorded method | Universal savings, statistical significance, a testimonial without consent |

All saved replay cards currently show possible later responses. Do not invent an unanswered card or describe a historical review as currently unresolved to improve the story. The app's unverified model rationale is retained as a visible limitation, not silently edited into a more convincing result.

## Record a real trial without manufacturing evidence

Use `docs/09-TRIAL-GUIDE.md` for the full comparison protocol. For a short comprehension trial, record date/release, anonymous participant ID, role, PR familiarity, help provided, observed actions, actual words and any failure. Ask the participant to explain historical versus live data, possible response versus code verification, and local versus GitHub effects. Do not supply the intended answers before asking.

Record elapsed and correction time only if actually measured, including help and waiting. The five-minute invitation is an estimated commitment, not a measured completion claim. The public replay's familiar, curated example is not a controlled performance comparison against GitHub reading.

If nobody completes a trial, report plainly: **“No genuine contributor trial conducted; available evidence is engineering and demonstration evidence.”** Preserve negative results and unresolved problems. No person, feedback, result or recording may be invented to complete the submission checklist.
