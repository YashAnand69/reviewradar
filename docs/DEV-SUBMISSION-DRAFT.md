*This is a submission for the [Hacktoberfest Open-Source AI Challenge Week 3: Slow and Steady](https://dev.to/challenges/hacktoberfest-week3-2026-10-19).* 

## What I Built

A review can ask for a screenshot in one place, describe a bug in another, and receive an author reply several days later. A PR status compresses that conversation into a label. The small chore I wanted to address was finding the original ask again and reading it beside the relevant reply.

**ReviewRadar is a local evidence workbench for selected public PRs you authored.** Gemma identifies individual human-reviewer requests and proposes relevant later author responses. The app places those original passages beside each other, with their dates and GitHub links. You inspect the context, keep a local note, and decide what deserves another look.

The input came from my actual open-source contribution history. For example, an [Eventyay review requested screenshots or a video](https://github.com/fossasia/eventyay/pull/6104#pullrequestreview-5396298833). A [later author update reported adding screenshots](https://github.com/fossasia/eventyay/pull/6104#issuecomment-5965628217). That pair is more useful to read together than as two disconnected notifications. It still does not establish that the screenshots were sufficient or that a maintainer was satisfied.

There are three separate states throughout the interface:

- What GitHub reported when the snapshot was fetched: PR/review/thread state.
- What the model suggests: a request and a possible conversational response.
- What I decided locally: reviewed, reopened, or a note for later inspection.

No button comments on GitHub, resolves a thread or marks code correct. That boundary keeps a reading aid from quietly becoming an authority over someone else's review.

## How I Built It

The browser is React and TypeScript. A local FastAPI backend imports public authored-PR discussions through the GitHub CLI, validates immutable source snapshots and stores analyses and local decisions in SQLite. Gemma 4 E2B runs through a pinned llama.cpp service. No GitHub credential is sent to the browser, and no hosted inference API is involved.

The first model prototype failed in an instructive way. It treated an author update, approval text and an empty review as requests. Another version altered punctuation while trying to quote a source. Valid-looking JSON was clearly not enough.

I changed the model's job. The application now builds exact source passages with stable keys. The model selects those keys; the server supplies the original text. The pipeline separates request extraction from response matching. Each request's response choices are restricted to existing, strictly later author passages, plus an explicit no-response option. Both stages check the actual runtime context budget before generation.

This prevents invented quotations and mechanically impossible source references. It does not prevent every wrong interpretation, so the original comment, surrounding chronology and uncertainty remain available. Oversized input, invalid output or a failed PR cannot quietly become an empty “all clear” queue. Switching to the no-model baseline is an explicit choice.

The interface follows that same principle: evidence first, explanation second. It has reversible local decisions, notes, source filters, source JSON and Markdown export. Transitions are restrained, and reduced-motion rules are included. Rendered accessibility and mobile checks must be completed before the final entry is published; automated DOM tests alone cannot establish those properties.

## What the Checks Actually Showed

The engineering pilot used four PRs and seven pre-labelled requests, with whole PRs separated between development and holdout. These were assistant-created engineering annotations, not independent customer ground truth.

The frozen v8 holdout found the three labelled requests and also emitted one quoted repetition as an extra request. That failure led to a quoted-text selection restriction. The next run is reported as a regression, not a fresh holdout; it still emits an additional agreement/observation as a possible ask. I kept that limitation in the [evaluation report](https://github.com/YashAnand69/reviewradar/blob/main/evaluation/REPORT.md).

The recorded checks include backend/adversarial tests, frontend state/workflow tests, type/build checks, an actual GitHub-import-to-inference API run and clean-source installation. The public preview is saved evidence, not a way to disguise unavailable inference. I have not obtained a genuine participant trial or measured a human time-saving percentage, so I make neither claim.

## Why Does Open Innovation Matter?

The model is the component that reads the language of the request and considers a later reply. It is central to the feature, rather than an unrelated integration added to a dashboard.

Running open weights locally lets me retain a dated input, inspect the model/prompt/runtime configuration, rerun a case and preserve a failure without paying for another hosted inference call. After installation and import, saved-discussion processing works without internet. Fresh GitHub imports and the initial dependency/model downloads still require a connection. This release supports public PRs, so I am not claiming an unimplemented private-repository privacy feature.

The [Gemma artifact](https://huggingface.co/ggml-org/gemma-4-E2B-it-GGUF) and [llama.cpp](https://github.com/ggml-org/llama.cpp) make the core workflow inspectable and replaceable. The repository pins the revisions/checksums used in the demonstration. Local execution still uses memory, electricity and installation time; “no hosted API bill” does not mean free of every cost.

## The Human Role

I chose ReviewRadar from the researched Week 3 ideas and asked for careful planning, separate reviews and staged implementation before submission. My contribution history supplied the real discussion examples and the context for the problem. Those are the human inputs I can substantiate.

AI agents assisted research, planning, implementation, testing and this write-up. I am not presenting their work as code I manually typed or an experiment with customers. The app also preserves a human role during use: only the person reading the actual evidence decides what their local review note should mean. A generated “possible response” never closes that decision for them.

## Current Limits

The model can miss a request, over-extract agreement or associate a reply poorly. Automated comments remain visible in Sources but are outside the explicitly labelled human-review queue. Large discussions can exceed the bounded context; the app rejects them visibly rather than silently dropping text. Private repositories, background monitoring and code-fix verification are outside this release.

The intended payoff is a calmer way to resume a review session. Whether that saves someone enough total reading and correction effort to become a regular habit is the next genuine-user question, not a result I can manufacture from test counts.
